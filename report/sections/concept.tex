This section presents the architecture and implementation of our real-time 3D spatial understanding system for visually impaired navigation assistance. The entire system is built around a low-latency \emph{LiveAgent} that orchestrates user interactions and tool calls. This agent is powered by the Gemini Live API, which allows it to provide real-time text responses, while Voice2Voice interaction remains a future goal.

\subsection{System Architecture}\label{subsec:architecture}

The system architecture implements a modular, event-driven design centered around three core components: the \textbf{Live Agent}, the \textbf{Scene Understanding Pipeline}, and the \textbf{Spatial Processing Pipeline}. The architecture follows the actor pattern (\autoref{fig:live-agent-component}) to ensure thread-safe communication and real-time responsiveness. All data flow is strictly typed using Pydantic models ensuring schema validation at every interface and enabling robust error handling throughout the pipeline. Figure~\ref{fig:system-arch} illustrates the overall data flow, which is triggered either by a user query or a frame change.

\subsubsection{Live Agent}

The Live Agent implements an asynchronous actor-based architecture that manages real-time interaction with users while orchestrating complex spatial analysis tasks. The component operates through a finite state machine that coordinates tool execution, response generation, and user communication without exposing intermediate processing steps.

\paragraph{Actor Pattern Implementation.}

The actor pattern (\autoref{fig:actor-pattern-component}) ensures thread-safe communication through typed message passing. Commands (\texttt{AskCmd}, \texttt{AudioCmd}, \texttt{SetFrameCmd}) are queued from the user interface thread, while events (\texttt{TextEvt}, \texttt{AudioEvt}, \texttt{DetectionsEvt}, \texttt{ErrorEvt}) are emitted to update the interface. This design prevents race conditions and enables responsive user interaction while background processing tasks execute asynchronously.

The agent maintains separate queues for incoming commands and outgoing events, with a dedicated asyncio event loop running in a background thread. This architecture allows concurrent operations, such as processing user queries while maintaining active audio streams for voice interaction.

\paragraph{FSM for Interaction Management.}

The agent employs a finite state machine with three primary states: \texttt{COLLECT\_FIRST} to capture intermediate outputs, \texttt{WAIT\_TOOL} during tool execution, and \texttt{COLLECT\_FINAL} for response generation. This state management ensures that tool outputs are processed internally before presenting final results to users to maintain a natural conversation flow.

When users pose spatial queries, the agent analyzes requests to determine whether qualitative description suffices or quantitative tool invocation is required. Keywords such as "where," "distance," "how far," and "spatial relationship" trigger tool usage, while general scene descriptions rely on the vision-language model's inherent capabilities.

The Live Agent implements a simple finite state machine (FSM) to manage the interaction flow, allowing it to ``reason'' about the current state and decide when to call tools or respond to user queries.
It maintains separate queues for incoming commands and outgoing events, with a dedicated asyncio event loop running in a background thread. This architecture allows concurrent operations, such as processing user queries while maintaining active audio streams for voice interaction. The \texttt{GeminiLiveAgent} together with related classes is depicted in \autoref{fig:live-agent-component}.

\paragraph{Tool Integration.}

The agent is given two primary tools for spatial analysis: \texttt{run\_aabb\_detection} for object detection and spatial analysis, and \texttt{get\_last\_detections} for retrieving cached detection results into the current ego frame. The detection tool supports four operational modes: \texttt{subset} for specific object queries, \texttt{hazards} for safety assessment, \texttt{navigation\_landmarks} for wayfinding, and \texttt{path\_description} for comprehensive route planning.

Tool responses are structured according to predefined schemas that include 3D coordinates in ego-centric reference frames, depth measurements in meters, directional information using intuitive clock notation (12 o'clock = straight ahead), and height measurements relative to the detected ground plane. This standardization enables consistent spatial reasoning across different query types and interaction modalities.

The system employs a relatively low temperature setting (0.1 \( \dots \) 0.2) to promote adherence to tool usage instructions and reduce hallucination. While code execution capabilities are available for spatial computations like pair-wise distances, the system primarily relies on structured tool calls to ensure predictable and reliable spatial analysis.


\subsubsection{Dataset Loader}
The \texttt{StrayDataset} provides frames through its \texttt{\_{}\_{}getitem\_{}\_} method. It loads the RGB image \(\I\), the depth map \(\Z\), adapts the intrinsics \(\K\), retrieves the camera pose \(\T_{WC}\) and optionally estimates the ground plane \((\nhat,d)\). The fields are returned in a \texttt{DatasetOut} structure.

\begin{algorithm}[H]
\caption{Dataset Loader}
\label{alg:dataset_loader}
\begin{algorithmic}[1]
\STATE \textbf{Input:} frame index \(i\)
\STATE \textbf{Output:} DatasetOut\((i,\I,\Z,\K,\T_{WC},(\nhat,d))\)
\STATE \(\I \gets \text{load\_rgb}(i)\)
\STATE \(\Z \gets \text{load\_depth}(i)\)
\STATE \(\K \gets \text{adapt\_intrinsics}(i)\)
\STATE \(\T_{WC} \gets \text{get\_pose}(i)\)
\IF{ground plane enabled}
    \STATE \((\nhat,d) \gets \text{estimate\_ground\_plane}(\I,\Z,\K)\)
\ENDIF
\RETURN DatasetOut\((i,\I,\Z,\K,\T_{WC},(\nhat,d))\)
\end{algorithmic}
\end{algorithm}

\subsection{Scene Understanding Pipeline}

The scene understanding pipeline (\autoref{fig:scene-understanding-component}) transforms RGB images into structured object detections through zero-shot prompting of Gemini 2.5. This component handles the complex process of extracting semantic and geometric information from visual input without requiring task-specific training.

\subsubsection{Gemini Detection}

The pipeline sends an RGB image along with detection mode specifications and user prompts to Gemini~2.5. The vision-language model returns a JSON list conforming to a minimal schema containing object labels, normalized bounding box coordinates, and base64-encoded segmentation masks. \\

Multiple validation steps are implemented through Pydantic model validators to handle malformed or schema-violating outputs. When validation failures occur, the system automatically retries the detection request up to a configurable number of attempts, ensuring robust operation despite occasional model inconsistencies.

\subsubsection{Mask Processing}

Mask processing begins with probabilistic masks from the vision-language model, which are first aligned with bounding box coordinates and resized to match the full image resolution. Binary thresholding converts probability values to binary masks, followed by morphological erosion using a \(3 \times 3\) structuring element to reduce the impact of false positives in the segmentation masks. This process is detailed in \autoref{alg:mask_processing}.

\begin{algorithm}[H]
\caption{Process Mask: Thresholding, Resizing, and Erosion}
\label{alg:mask_processing}
\begin{algorithmic}[1]
\STATE \textbf{Input:}
\STATE \quad Prob. mask \(\hat{\mathbf{M}} \in [0,1]^{h \times w}\)
\STATE \quad AABB \(\mathbf{b} = (x_0, y_0, x_1, y_1)\)
\STATE \quad Image size \(H \times W\)
\STATE \quad Threshold \(\theta \in (0,1)\)
\STATE \quad Structuring element \(\mathbf{S}^{(3)} \in \{0,1\}^{3 \times 3}\)
\STATE \textbf{Output:}
\STATE \quad Eroded binary mask \(\mathbf{M}' \in \{0,1\}^{H \times W}\)
\STATE \(\mathbf{M} \leftarrow \text{AlignWithBoundingBox}(\hat{\mathbf{M}}, \mathbf{b}, H, W)\) \COMMENT{Resize \& align w/ AABB}
\STATE \(\mathbf{M} \leftarrow [\mathbf{M} \geq \theta]\) \COMMENT{Threshold to binary mask}
\STATE \(\mathbf{M}' \leftarrow \mathbf{M} \ominus \mathbf{S}^{(3)}\) \COMMENT{Erode mask}
\RETURN \(\mathbf{M}'\)
\end{algorithmic}
\end{algorithm}


\subsubsection{Depth Computation}
Depth computation employs a robust statistical method to handle noisy depth measurements. The system extracts valid depth values from the masked region and computes depth statistics using Median Absolute Deviation (MAD) for outlier rejection:

\begin{equation}
    d_{MAD} = \min\bigl\{d \in \mathcal{D}_{\text{valid}} : L \le d \le U \bigr\}
\end{equation}

\begin{equation}
\begin{aligned}
\mathcal{D}_{\text{valid}} &= \{d \in \mathcal{D} : d > 0\},\\
m &= \mathrm{median}\bigl(\mathcal{D}_{\text{valid}}\bigr),\\
\mathrm{MAD} &= \mathrm{median}\bigl(|\mathcal{D}_{\text{valid}} - m|\bigr),\\
L &= m - k_{L} \cdot \mathrm{MAD},\quad U = m + k_{U} \cdot \mathrm{MAD},\\
\end{aligned}
\end{equation}

The final depth estimate \(d_{MAD}\) is the minimum valid depth value within the computed bounds \([L, U]\), providing robustness against depth sensor artifacts, occlusion effects and false positive mask regions.

\subsubsection{3D Center Point Computation}

Object center points are computed in both image and world coordinates to support spatial reasoning. The 2D centroid is determined using median coordinates of the eroded mask to ensure robustness against asymmetric object shapes:

\begin{equation}
\mathbf{p}_{\mathrm{centroid}}
=
\begin{bmatrix}
u_{\mathrm{centroid}}\\[6pt]
v_{\mathrm{centroid}}
\end{bmatrix}
=
\begin{bmatrix}
\displaystyle
\mathrm{median}\bigl(\{\,u \mid \mathbf{M}'(u,v)=1\}\bigr)
\\[10pt]
\displaystyle
\mathrm{median}\bigl(\{\,v \mid \mathbf{M}'(u,v)=1\}\bigr)
\end{bmatrix}
\label{eq:centroid}
\end{equation}

The 3D center point in camera coordinates is computed by back-projecting the 2D centroid using the robust depth estimate and camera intrinsics:

\begin{equation}
\mathbf{p}^c
=
d_{\mathrm{MAD}}\;\mathbf{K}^{-1}
\begin{bmatrix}
u_{\mathrm{centroid}}\\[4pt]
v_{\mathrm{centroid}}\\[4pt]
1
\end{bmatrix}
\end{equation}

\subsubsection{Directional Estimation}
Object orientation relative to the camera is expressed using both angular and clock-based notation for intuitive user interaction. The yaw angle \(\psi_{\text{deg}}\) represents rotation around the vertical axis in the horizontal plane, computed from the 3D position:

\begin{equation}
\begin{aligned}
\psi_{\text{deg}} &= \arctan2\left(x^c, z^c\right) \cdot \frac{180°}{\pi} \\
\psi_{\text{clk}} &= \left\lfloor \frac{\psi_{\text{deg}}}{30°} + 0.5 \right\rfloor \bmod 12
\end{aligned}
\end{equation}

The clock position \(\psi_{\text{clk}}\) provides an intuitive directional reference where 12 o'clock corresponds to straight ahead, 3 o'clock to the right, and 9 o'clock to the left.

\subsubsection{Estimating Height Relative to the Ground}
Height estimation relative to the ground plane utilizes the RANSAC-derived plane parameters. For any 3D point \(\mathbf{p}\), the height above the ground plane is computed as:
\begin{equation}
h = \nhat^{\top} \mathbf{p} + d.
\label{eq:height}
\end{equation}

\subsubsection{Inter-Frame Coherence}

To maintain spatial coherence across temporal sequences, the system implements SE(3) transformations that convert detection coordinates between different camera poses. When frames change, relative motion is computed and communicated to the Live Agent through descriptive system messages.

The transformation from pose \(\T_A\) to pose \(\T_B\) is computed as:
\begin{equation}
\T_{rel} = \T_B \T_A^{-1},\quad
d = \|\boldsymbol{\tau}_{rel}\|,\quad
\psi = \operatorname{atan2}(-R_{32}, R_{11}).
\label{eq:relative_motion}
\end{equation}

The translation vector \(\boldsymbol{\tau}_{rel} = \T_{rel}[:3, 3]\) is the relative motion in meters, and \(\psi\) is the \emph{yaw}-rotation around the \emph{vertical} axis. \( R_{32} \), and \( R_{11} \) contain the negative sine and cosine of the rotation angle, respectively.\\
We then provide the model with a system message, that describes the relative motion, and also provide it with an overview of all cached detections from previous frames.


\subsubsection{Data Structure Integration}

After processing, all spatial attributes are encapsulated in structured \texttt{AABBDetection} objects that include normalized bounding boxes, processed masks, depth statistics, 3D center coordinates, rotation measurements in both degrees and clock notation, and height relative to the ground plane.
\begin{equation}
\texttt{AABBDetections} = \{ (\pc, \|\pc\|, \psi_{\text{clk}}, \psi_{\text{deg}} \bbox, h)^{(i)}\}_{i=1}^{N}
\end{equation}

The resulting detections can be efficiently cached and transformed across frames, supporting multi-view spatial reasoning and enabling the system to reference previously detected objects without recomputation, thereby improving both performance and temporal consistency in navigation assistance.
